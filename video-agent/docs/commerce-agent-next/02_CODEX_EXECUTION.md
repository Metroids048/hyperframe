# 给本地 Codex 的总控与连续实施 Prompts

用途：修改现有项目。不是用于让产品直接制作视频的运行时 Prompt。运行时 Prompt 在 03 文档，必须被接进产品主调用。

## A. 开发总控 Prompt

你现在负责修改现有 Metroids048/hyperframe 项目，交付真正由应用 Agent 完成的高质量电商视频制作闭环。阅读同目录 01_SOLUTION.md、03_RUNTIME_PROMPTS.md、04_BENCHMARK_AND_ACCEPTANCE.md，再连续执行本文件 Loop 00—07。

### 目标

用户只需在现有浏览器聊天界面描述需求并上传可选素材，应用就能理解任务、观察素材、按需加载和执行 HyperFrames 的技能/模板/组件/蓝图/受审插件，完成分层创意规划、镜头制作、预览检查、局部修复和完整输出。视频不是只有 15 秒的图文卡；在资料充分时，45/60/90/120 秒任务也应有真实内容推进和视觉设计。后续对话继续编辑同一个原生工程。

这次最重要的是缩小“直接 Codex 调 HyperFrames”与“产品内调用”的质量差距。增加提示词长度、资源注册数量或单测数量不构成交付。

### 先读并尊重本地状态

1. 读取根目录和所有适用的 AGENTS.md/嵌套工作区规则，识别真正应用目录和启动方式。
2. 记录本地 HEAD、分支、锁文件、工作区 diff、未跟踪内容、已有输出、端口与依赖版本；只在项目范围内检查与本任务有关的配置和资源，不能扩大到扫描整台机器或读取无关凭证。
3. 远程参考快照为 4848b72，但本地可能更新。不得为对齐方案自动 pull/checkout 覆盖、reset --hard、git clean、force push、自动 stash 或删除已有输出。不要自动提交或推送。
4. 测试和参考片使用隔离的目录、端口与项目 ID，不修改用户真实作品。保留历史失败证据。
5. 将本方案和现有 Pxx/Loop 任务建立映射。已实现的项目能力复测后复用，不重复造一套内核、文档、前端或渲染器。

### 不改变的边界

保留浏览器 WebUI 和既有模型登录/提供方，不让用户日常操作 CLI。本轮不新增生图、生视频、数字人、投放服务，不自动启用收费 API，不创建复杂多 Agent 平台。CLI 可以是内部受控工具，但不是用户聊天界面。

单文件、单项目素材数、600 秒、30fps、1080p 级输出等边界，以本地现有合同为准复核并保留。不要把原有能力缩成只做演示短片。原有语音/音乐能力只在有要求且可用时使用。

### 产品设计要求

1. 先理解这次用户请求与输入，再组合制作步骤。业务场景只是检索标签，不能成为必须选择的菜单或单一互斥分支。
2. HyperFrames 不仅负责最后导出。其技能、引用规则、蓝图、样式和资源应真正进入创意与构建过程。目录存在、注册存在、模型声称已使用，不等于实际接入。
3. 普通商家短需求和详细 Brief 都要成功。不能要求用户先给完整分镜和 GSAP 方案，才能得到合格成片。
4. 保留结构化主控，但不要用僵硬的每场两个媒体、三条文字、12 幕等限制充当所有内容的上限。改为分层叙事、时间错开、资源合同和本机预算。若保留限制，必须明确其局部适用范围。
5. 将主导演的一次大请求拆成可恢复的需求/资源/故事/计时/镜头制作/评审阶段。确定性步骤不调用模型，小修改走短路径。
6. 保留并完善受控原创。允许经过测试的布局、媒体 wrapper、品牌字体/token、安全图形和插件适配，不能为支持效果删除安全校验、运行任意脚本或放开系统权限。
7. 使用当前原生文档、受管源码 bundle、资源锁、稳定对象 ID 与版本。不得压平为 MP4 后声称可以编辑原始标题，也不得维护互相冲突的 JSON 与手改 HTML。
8. 所有质量修复都由应用运行链路执行和记录。开发者可以制作 reference-author 参考片，但不得把它当成 product-agent 输出。
9. 不靠延长 hold、重复模板、重复同一个商品图、无意义特效凑时长。检查每个段落带来的信息和依据。
10. 完整试听/播放、事实、画面可读性、动作完整性与局部修改正确性，优先于“文件存在/语法通过”。

### 执行方式

按 Loop 00—07 的依赖连续执行；不在每个 Loop 后问用户要不要继续，不在完成审查或单测后停成总结。每轮都走：复核 → 最小实施 → 运行 → 检查真实结果 → 修复 → 记录证据 → 下个未阻塞任务。

每次修改代码后，先在本地运行适用检查和测试，再交付该部分代码。测试命令从 package.json/本地实际脚本核实，不运行假想命令；需要新增测试时先实现再运行。

输出修改必须进入真实应用入口。单独脚本、手写 JSON 夹具或绕过 UI 的内部调用只能算单元/集成证据，不能替代产品验收。

模型额度、必需素材、授权或真人评审缺失时，清楚标记阻塞，不模拟成功、不擅自切收费提供方；继续其他无依赖任务。需要用户决定时只问无法从现有项目与材料解决的那一项，不重复询问已给信息。

单次会话工具预算/上下文不足时，保存已完成状态、证据和精确续跑位置。本次回复报告真实成果和未完成项，不承诺后台继续，也不要把中断写成全部完成。

### 必须维护的执行记录

使用本地现有等价结构；没有则在本方案目录或项目测试输出目录创建：

- EXECUTION_STATE：Loop、任务、状态、依赖、当前基线、缺陷、下一步。
- CHANGE_IMPACT：新增/修改/复用能力与调用位置。
- RESOURCE_AUDIT：来源、版本、依赖、许可、兼容性、已激活状态及证据。
- RUN_EVIDENCE：请求、素材哈希、模型/工具/资源、项目与版本、视频和检查记录。
- BENCHMARK_RESULTS：直接参考、旧应用、改造后应用的配对结果。
- KNOWN_LIMITATIONS：未支持资源、剩余视觉缺陷、阻塞原因及恢复方式。

状态至少区分 implemented、verified-code、verified-media、verified-product、needs-human-review、blocked。某项单测通过只提升对应状态，不允许直接从 implemented 跳到 commercial-ready。

### 最终回复必须包括

实际本地基线、保留了什么；相对原版本改了什么；哪些 HyperFrames 资源实际进入主链路；第一条 60 秒片与 90/120 秒等成片、原生工程、真实浏览器证据的位置；当前运行测试和失败项；对照实验结果；仍未完成的内容和确切原因。不得只说“20/20 通过，所以已全部完成”。

## B. Loop 00：现场基线与同输入差距实验

阅读总控，然后实施：

1. 核对工作区、源码、入口、依赖与已存在的 Agent 运行路径。明确 creative/service 是否接 AgentKernel，skill 指令在哪里加载，custom 源码允许什么，导出实际执行什么。
2. 保存当前工作区指纹：HEAD 加相关文件内容哈希，不能只写 Git 提交。
3. 选择素材足够、可追溯的一个 60 秒商品任务。冻结原始素材、用户短请求、商品事实、声音政策与画幅。
4. 在隔离目录记录当前应用真实输出；通过相同素材和要求让直接 Codex 使用当前可用 HyperFrames 方法形成 reference-author 参考。不能添加额外素材或专家分镜帮助参考组却不给应用组。
5. 记录模型与版本/设置/技能/工具/人工干预/渲染配置差异，逐时间段比较内容、布局、动效、声音和改动能力。直接参考本身不合格就明确记下，不能假定它必然正确。
6. 将发现区分为代码事实、实测失败和待验证假设，排列最影响质量的三个瓶颈。

产物：基线报告、冻结任务、全部尝试记录和差距假设表。存在 provider 阻塞时保留待跑项，并继续可完成的能力适配；不能伪造 reference 视频。

门槛：知道“差在哪里及如何测试”，而不是只知道模板数量。

## C. Loop 01：HyperFrames 能力与资源真正可调用

基于现有 registry、runner 和工具层实现：

1. 探测安装版本及可用命令，在当前稳定环境建立资源接入合同。
2. 从已授权/公开的官方目录发现 skills、依赖引用、scripts、示例、Blocks、Components、动效蓝图、品牌样式及运行时适配器。固定来源和版本，不只复制技能标题。
3. 建立需求/镜头级检索和依赖解析；区分 guidance 与 executable。记录兼容性、素材前提、可编辑字段、代码与媒体许可。
4. 任务按需读取技能正文和关键引用，模型看到的工具表只列实际可执行项。
5. 适配至少三种具有实际差异的需求所需资源：真实视频叠层包装、多图细节/比较、字幕或复杂文字。数量不是验收指标，每一种都要由主链路调用并产生原生可编辑对象。
6. 对未兼容资源显式标记，不自动升级生产依赖。确需升级时做隔离实验和旧项目回归。

测试：缺依赖、离线缓存、版本冲突、中文长文案、横竖方、错误资源输入、外链/越权资源拒绝、技能摘要未加载完整上下文等案例。

门槛：从请求追到“具体技能内容/资源文件 → 工具执行 → 可见场景 → 可修改对象”，不是看到 registry 里多了几行。

## D. Loop 02：需求驱动的主控工作流

1. 复用并接通已有 AgentKernel/服务；不要平行新增另一套项目库。核对已有 run store 的写入原子性、重复执行和并发行为，必要时修复。
2. 增加需求规格、持久约束账本与可组合任务计划。阶段定义参考 01 文档，Prompt 参考 03 文档。
3. 新建走完整工作流，已有作品的小修改/导出走短路径。不要每轮重新问时长、风格和素材。
4. 给运行时提供受控工具调用回路；可以使用现有 provider 返回结构化下一步，由服务执行真实工具，再将结果返回下一轮。不要要求不存在的 provider 原生函数调用能力。
5. 将技能/引用选择、素材证据和阶段输出传入真实模型；记录输入输出证据，避免一次请求塞全部素材和全部源码。
6. 设置合理的任务/镜头/资源预算、取消、恢复和错误分类。调度预算与视频内容规模关联，但有硬上限。
7. 简短请求在 WebUI 得到可执行制作计划与真实预览；现有确定性字幕/撤销快捷路径保留。

测试：跨场景混合需求、无场景名输入、已有工程的局部修改、连续 10—14 轮约束保留、任务中断恢复、重复请求、导出期间编辑与权限负例。

门槛：真实 WebUI 请求能经过完整能力工作流；不是测试脚本拥有该能力，产品仍用旧单次调用。

## E. Loop 03：制作能力与第一条 60 秒质量成片

这是第一条关键交付链，不要继续堆文档来回避效果问题。

1. 将故事规划与具体镜头源码生成分离。让镜头工作包包含实际素材、邻接镜头、品牌规则、时长、选定资源和编辑合同。
2. 实现/接入镜头级制作步骤：静态关键画面 → 布局检查 → 动效 → 过渡与媒体同步 → 场景预览。
3. 解决 Loop00 验证过的表现瓶颈。特别验证受管视频多窗口/画中画/安全裁切、商品细节标注、中文排版、品牌字体与相继出现的文字。不要只添加更多颜色。
4. 扩展自定义布局时保持实际视频仍由 HyperFrames 控制播放与时钟。不得通过允许任意 script、fetch 或系统命令绕过限制。
5. 从同一母工程产生代表性 10—15 秒预览，执行真实视觉检查与有界修复。预览批准/默认自主继续的策略按原用户偏好执行。
6. 由应用从 Loop00 相同输入生成完整 60 秒成片，全部通过原生工程输出。不得将 reference-author 的成片/完整代码复制为产品结果。
7. 至少完成一次用户短指令续改和撤销，再完整渲染核对。

测试：媒体窗口对齐、变换与 seek、重复节点、字体缺失、长字幕溢出、恶意 SVG/CSS、取消/失败回退、预览/导出一致。

门槛：有一条可以完整观看的 60 秒产品自动生成片，内容与视觉明显超过旧应用；差距用时间点/画面对照记录。未达标时保留缺陷并迭代本 Loop，不靠增加毫无关系的功能冲过。

## F. Loop 04：90/120 秒叙事、声音计时和更长任务

1. 实现段落—节拍—镜头—对象的分层计划，按需扩展/迁移现有 schema，保持旧项目兼容。
2. 修正固定场景数、每场同时出现文字和统一重叠等妨碍内容组织的通用约束；安全限制保留为明确的资源预算。
3. 实测旁白/原声/动作时间，使用明确锚点组织字幕和强调；不要简单按字符猜配音时长。
4. 对足够素材运行 90 秒混合内容和 120 秒讲解/口播任务，再执行 180 秒边界内真实叙事任务。600 秒可先做明确标记的结构/渲染压力测试，不冒充高质量商业样片。
5. 检查每段是否引入新信息、是否保留完整动作、是否持续重复大字卡或同一图。不用拉长 hold 或无意义慢放补时长。
6. 缓存分析和已通过镜头，按依赖失效；节制并行，在本机测量内存与耗时。

门槛：60/90/120 秒不仅时长正确，叙事、声画和可修改性也通过；短片请求没有被强行改成长片。

## G. Loop 05：复杂续改、版本和原生资源一致性

1. 新接入的官方组件和原创场景都支持对象级修改；必要时声明只读/受限参数，不能假装全部可改。
2. 实现修改影响分析，保留未相关对象/素材/声音与锁定内容；选择性撤销动效不撤销后来的改价。
3. 验证改价、替换商品图、调整一段速度/时长、换配音句子、重做中段布局、改画幅和开头分支。
4. 所有变更写回原生文档/受管 bundle，不允许只写派生 HTML。
5. 完成导出快照隔离、工程包重开/续改、旧项目回归和中断恢复。

门槛：同一 60/90 秒工程在真实对话里连续改 10—14 轮仍正确，版本关系和未修改部分有证据；不是不断重新做整片。

## H. Loop 06：完整质量闭环与工作台呈现

1. 质量分工程、内容事实、视觉叙事、声音、授权/发布状态，不能用一个 check 通过代替所有结论。
2. 增加基于真实渲染帧/短片段的评审与修复工具，把问题定位到时间和对象；保留原始失败和修复次数。
3. 对完整成片检查黑帧/缺图/音画不同步/字幕越界/动作断裂/价格条件遗漏/不必要重复。
4. 在原有 WebUI 做最小必要呈现：当前制作阶段、范围预览、可继续修改的对象/版本、缺口和明确交付状态。不设计强制场景菜单或另一套 UI。
5. 固定预设与重新生成继续清楚区分。主展示换为当前真实生成的 45—120 秒任务，保留简短回归示例但不把它们当旗舰。

门槛：普通用户从输入到完整预览、修改、导出能走通；系统失败时也知道保留了什么、缺什么，不静默降级。

## I. Loop 07：盲测、回归和最终交付

1. 按 04 文档冻结开发样本与未见需求，用相同条件生成 reference-author、baseline-product 和 current-product，保留全部尝试和失败。
2. 完成主力 Demo、短片回归、压力边界和至少 10 个未用于定向优化的组合 Brief；报告样本范围，不能从小样本声称所有电商需求完成。
3. 真实浏览器复跑：上传、发送短请求、预览、续改、取消/恢复、导出、重开工程。录屏与请求日志对应同一个 run。
4. 实际执行 package.json 中适用测试，再运行本轮新测试。旧的通过数不代表新版本通过。
5. 计算工程成功率、首稿/修复后质量、时长达标、无关内容变化、时间/成本、未见任务结果。没有真人评分就保留待审核，不编造独立 85 分或投放收益。
6. 更新 README、能力表、资源兼容性表和版本说明；将废弃的限制、示例专属价格规则和过时状态明确处理。

门槛：交付“真实应用能完成的范围＋对应证据＋剩余问题”，不是“所有功能都完美实现”的无证据结论。

## J. 会话中断后的续跑 Prompt

读取本地适用工作区规则、同目录设计文件和上次 EXECUTION_STATE/证据。先重新核对当前 HEAD、相关 diff、进程、项目版本与资源锁。不要重跑已通过且输入未变化的昂贵任务，也不要沿用与当前源码不匹配的通过结论。找到第一个未完成且未阻塞的任务，按 Loop 依赖继续实施、运行、检查、修复并更新状态。保留用户全部未提交工作，不重新问已记录的产品目标，不退回只写方案。最终说明这次实际补完的部分、成片和证据，以及仍受阻项。
