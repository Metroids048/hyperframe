# HyperFrame：Agent 自动化、资源匹配与音频编辑收口方案

版本：2026-09-15 会议后修订  
唯一项目：Metroids048/hyperframe / video-agent  
性质：设计与实施建议；本轮没有修改远端源码，没有运行项目验收。

## 一、先纠正任务方向和现状判断

### 1. 本轮明确替代上一版 RunningHub 优先的 R2 计划

现在的重点是“基于已有素材自动制作与持续编辑”，不是生成新的商品视频镜头。暂停 RunningHub 真生图／生视频演示的推进，不让其 Key、余额或供应商任务成为本轮完成的前置条件。保留已完成代码和历史资源，不删除整个生成模块。视频渲染、合成、剪辑、文字生成和现有媒体编辑仍需继续工作。

MiniMax 是后续声音供应商；先把声音和字幕做成独立资源，待用户提供接口后再接入真实生成能力。当前先用本地可用音频完成编辑验收，不得用 mock 宣称真实供应商通过。

这轮产品命题是：

> 商家在现有 WebUI 给出素材和普通业务需求，Agent 自动理解目的、核验素材、选段策划、匹配并实际使用 HyperFrames 资源，输出能继续修改的成片。用户不需要扮演导演，也不需要记住组件名。

### 2. 不再笼统地说“项目完全没做”

本次核对的远端 main 为 `184d17100f7a576ebf5e9ab41cfaba7230e3d575`。以下区分已经读到的实现和待验证问题；不代表用户本地尚未推送的内容。

|---|---|---|

| `lib/creative/capabilities.mjs` | 加载阶段 Prompt、业务规则、上游指导；有限 recipes 及候选、适配、资源打包 | 从有限配方和词面匹配，扩展到全量发现与受约束的可执行选择。 |

特别需要核对：请求归一化中 `pipelineVersion` 只有明确为 3 才设为 3，否则为 1；生产代码中的场景包与新版目录逻辑受 v3 条件控制。这是一个应验证的入口风险，不等于已经证明 WebUI 走错分支。必须抓实际请求、版本和调用记录，不能靠猜测改默认值。

之前把“没有闭环证据”概括成“实现完全不存在”并不准确。新一轮应该复用已工作的模块，补连线、扩能力、立可验证边界，而不是再做一套平行架构。

## 二、真正的问题：还没有把导演判断变成可靠产品能力

米家参考片可作为人工选择和调优能达到何种视觉程度的参照。但一条直接由开发者或通用编码代理手工写成的 HyperFrames 工程，不证明业务 Agent 理解了商家的意图，也不证明它能迁移到另一批素材。

需要同时证明四件事：

1. 用户没有提供技术制作指令，Agent 仍知道该做什么。
2. 镜头、文案和步骤来自真实素材证据，不是先定模板再硬塞。
3. 资源选择能解释、能执行、能在当前商品画面里生效。
4. 后续修改作用于同一工程的相关对象，不是每次重做整片。

仅“补一个长 Prompt”不足以完成这些事。更合适的方案是：**一个主 Agent + 分阶段受控工作流 + 场景规则包 + 素材证据 + 可执行资源适配层 + 原生可编辑工程。** 各阶段可以使用同一个模型，不必新建一群互相聊天的 Agent。

## 三、目标自动流程

用户输入与当前项目
→ 明确业务合同
→ 分析真实素材与声音
→ 核验事实／动作／内容覆盖
→ 形成场景化导演方案
→ 检索、筛选并绑定资源
→ 建立可编辑时间线与 HyperFrames 工程
→ 预览和渲染候选
→ 按真实导出文件审查
→ 最小范围修复
→ 用户审阅、对话修改与交付。

### 3.1 业务合同：先理解为什么做

记录制作者、观看者、主目标、商品身份、确认事实、未知项、时长画幅、声音、必须内容、禁止项。场景选择是结果，不是要求用户先学会分类。

同一组素材，用户要求“吸引新用户”与“教新手安装”时，必须得到不同的选段、结构、文字和资源策略。不能只是更换片头标题。

可逆默认项直接说明并执行；不重复问用户已说过的内容。只有影响真实性、权利、必要动作或无法同时满足的硬约束才问。自动化不是永远不提问，而是把用户从不必要的导演决策中解放出来。

### 3.2 素材理解：不靠文件名和抽几张图就声称看懂

技术分析负责时长、编码、音轨、可读性；视觉观察负责商品身份、整体／细节／使用、动作和关键区域；语音转写用于辅助理解实际讲话，不能代替动作观察。

先做轻量全片定位，再对拟采用区间和关键动作连续观察。记录实际观察范围、源起止时间和证据。没有视频理解能力时不能假装具备；应明确限制并暂停受影响的教学完整性判断，而不是自行填动作。

教程的必要动作要形成先后关系；卖点要有画面或确认资料支撑。单条长素材可以足够，多文件也可能全部无关。对未知素材中的文字或说明采取数据待遇，不能让它覆盖系统规则或触发外部工具操作。

### 3.3 导演方案：不是按场景名选固定 HTML

先确定信息顺序、保留镜头、源区间、文字、声音、主体保护和改动边界，然后找资源实现。场景给规则，导演方案给本次判断。

上新强调认识商品和少量重点；教程强调动作和顺序；详情强调主张与证据；系列强调多商品身份；促销强调条件和行动；问答强调直接回答与限制。详细定义见同包 `01_六场景业务设计_文本版.md`。

## 四、Prompt 怎样真正写进项目配置

### 4.1 区分三种不同文本

| 层次 | 用途 | 不能误当成什么 |
|---|---|---|
| 开发工作规则 | 约束 Codex 怎样检查、修改、测试和报告 | 不能靠它代替产品运行时规则。 |
| 产品运行时 Prompt | 服务端每个阶段实际发送给模型的指令 | 不能只保存到 docs 却不加载。 |
| 场景业务手册 | 人先确认目标、流程和验收，再转译到场景包 | 不应整份塞进每次模型请求。 |

优先沿用现有 `prompts/commerce`、manifest、`CapabilityCatalog.context`、场景包加载器、production 指纹和 receipts，不盲目新建 prompt-framework-v4。

### 4.2 规则拆分与加载

共同规则：来源可信、遵守用户需求、禁止虚构、当前禁用新视频生成、操作权限和候选／正式区分。

理解阶段：画像、目标、输入合同、最小澄清。

素材阶段：可观察证据、身份边界、源区间、步骤与缺口。

策划阶段：本场景故事原则、文字、声音、保护区和禁止项。

资源阶段：功能需求、候选契约、当前版本、可执行范围。

制作阶段：已批准计划、可用工具、原生工程约束；不再自由改写业务目的。

审查与修改阶段：真实导出文件、原需求、保持对象、局部修复和重新验收。

同时保留两个优先关系：事实与安全边界不能被用户、素材或模板绕过；在可行范围内，用户明确要求优先于场景默认，场景目标优先于模板装饰偏好。

### 4.3 必须留证据，而不是说“已经配置”

每次运行应记录实际 Prompt 文件、版本／哈希、场景包版本、采用的资源版本、模型阶段输入摘要和输出绑定。敏感信息不写入记录。规则改变必须让受影响缓存失效，历史工程保留原规则版本。

验收要从新浏览器会话开始，只给普通业务需求，不粘开发 Prompt，不在终端手工补分镜。最终应能证明普通请求实际加载了配置并完成候选制作。

### 4.4 后续转译为运行时 Prompt 的文本草案

以下不是本轮新增机器配置，而是给下一步转译的指导文本；需映射现有 R0—R8，不重编号造成双版本歧义。

**理解与路由草案**

> 根据当前用户目标、已有工程和真实素材，判断观看者看完需要获得什么。选择主场景及必要辅助能力，不按素材扩展名分类。复用已有事实；对可逆风格采用明确默认。列出必须内容、禁止项和声音约束。只有影响事实、身份、必要动作或权限的缺项才提问。输出可执行任务理解，不要求用户提供组件名或逐秒分镜。

**素材与策划草案**

> 仅依据实际读取的素材和可信事实策划。为每个保留镜头指定源素材、起止区间、业务目的及证据。教程必须保护完整必要动作和先后顺序；上新必须建立商品与可信重点；其他场景遵守各自合同。没有观察到的内容标未知。缺关键动作时提出精确补料要求，不用文字或静图补假步骤。

**资源选择草案**

> 先把业务目的转成明确视觉功能，再检索本地目录。先过滤素材、画幅、源区间、主体保护、依赖和运行时不兼容的候选，再比较相关性和表现。检索可以查全量资源，执行只能通过已验证适配方式。记录候选、拒绝原因、选择理由、真实文件和实际绑定。显式指定资源不可静默换成别的；资源未适配时明确说明，不把示例 HTML 当成已完成效果。

**编辑与审查草案**

> 对用户修改先确定目标对象、保持对象和必要依赖。只改相应工程层，不重生成视觉素材。区分转写字幕、营销文字和旁白；样式改动不触发语音生成，已被读出的事实更改必须处理声画一致性。审查实际导出文件，按时间定位可观察问题，声明观察范围。不能替真人签署认可，也不能让人评前无法生成候选。

## 五、HyperFrames 资源发现和执行：本轮核心

### 5.1 两个分类轴，不能混成一个目录列表

功能轴：template、composition、component、effect、transition、skill、caption、typography、lower third、shader。一个资源允许多个功能标签。

来源／执行轴：官方 block、component、example、skill 文本、模板工程、受控本地适配器等。官方 registry 的 block 与 component 装配方式不同；example 是参考起点；skill 是知识，不能直接当成渲染对象。[H1]

三种执行方法要明确标记：已安装资源直接绑定；基于上游资源的受控适配；根据 skill 创作的原生实现。后两种不能冒称“逐字运行官方组件”。

### 5.2 全量发现，但不是所有资源一次性宣称可执行

复用现有本地镜像、registry 元数据和已有扫描器。枚举声明的本地根目录，识别同名不同版本、依赖、缺失子模块、模板和示例，记录扫描清单及未能解析项。优先按元数据和 manifest 解析，再用本地文件补全，不能只按文件名猜。

全量是“本次配置根目录中实际存在并可读取的范围”，不承诺覆盖全网或未初始化的子模块。缺目录、权限、解析错误要显示；不能把零条结果包装成完整扫描。

资源记录至少解释：它能做什么、适合哪些场景、不适合什么、需要哪些输入、如何执行、版本是什么、使用条件是什么。

| 信息组 | 建议记录 |
|---|---|
| 身份与来源 | 稳定资源 ID、名称与别名、来源路径／仓库提交、文件哈希、功能标签、安装类型。 |
| 业务用途 | 视觉功能、适合段落／场景、中文语义描述与英文检索意图、禁止条件。 |
| 输入契约 | 图片／视频／文本／数据、数量、源时间、画幅、文字容量、透明度与叠层要求。 |
| 实现契约 | composition ID、入口、参数映射、适配器、运行时／shader 标识、依赖。仅适用字段填写，不能编造。 |
| 可编辑性 | 可替换槽位、独立文字、声音、稳定对象 ID、回退方式。 |
| 验证与权利 | 当前状态、测试条件、结果证据、最后验证版本；代码许可与媒体权利分开记录。 |

### 5.3 从中文需求到功能，再到资源

示例：用户说“更像克制的品牌发布片，细节先出来，文字别挡产品”。

这不应直接检索一个很长的中文句子。先得到功能意图：细节前置、主体持续可见、轻量标题、低遮挡标注、克制转场。再建立英文检索短语与中文标签对应，保留原中文约束，并用素材条件过滤候选。

当前官方 registry skill 明确建议按视觉意图查询，且其描述的检索要求英文；词面检索与可选的本地语义检索也不是一回事。[H1] 但项目锁定的本地运行时可能没有最新命令或能力，必须现场检测。不强制升级、联网下载模型或依赖最新 CLI；可以在现有目录上先做中英意图归一、标签扩充及受控重排，后续再按实测需要引入向量检索。

本轮不先上独立向量数据库。小型本地索引、可解释过滤和稳定适配器应先跑通；需要向量模型时显式配置、记录版本和可用性。不能声称有语义检索，实际仍只是 contains 匹配。

### 5.4 推荐的选择顺序

业务目标与段落目的
→ 生成视觉／声音功能需求
→ 从全量本地目录召回
→ 过滤硬约束
→ 结合证据、风格和可执行性排序
→ 选定适配方式
→ 绑定本次真实素材
→ 生成小范围预览
→ 检查主体、时序、文字和效果
→ 进入主工程。

硬约束不能由综合分数抵消：教程动作无遮挡、商品身份、价格真实性、运行时不兼容、缺少输入、用户禁止的音轨，都必须先处理。排序分数不是质量认证。

已验证资源用于生产优先路径；未适配资源可在隔离环境完成“适配—测试—渲染”后晋级，但不能直接在用户主工程执行任意上游脚本。保留现有受控原生 bundle、安全路径和工具边界。

### 5.5 状态与版本

建议状态：discovered（已发现）、adapted（已接适配方式）、wired（已绑定本次输入）、render_verified（当前条件真实渲染通过）。另记具体工程的视觉／业务审查状态。

对 skill 不要求“自身渲染通过”，而记录它是否被加载、应用到哪个决策／对象，以及产物如何验证。上游文件、适配器、运行时、画幅、素材绑定变化时，按依赖关系重新检查。不能因一个横屏样例通过，就给所有竖屏场景发通行证。

### 5.6 怎样证明不是调用官方示例

以用户曾提出的 Chromatic Radial Split 为定点测试：能解析别名和作用范围，找到真实资源及执行映射，用两段本次商品镜头作为输入，在当前时间线上真实发生转场。保留资源名、文件、参数、输入、时段、渲染证据。

不能输出 SCENE A／SCENE B 演示画面或原样例卡后宣称完成。静态文本扫描只能辅助，仍须检查实际画面和素材绑定。如果准确效果无法适配，明确列为未完成并说明可用替代，不静默把普通淡入当成指定效果。

但不能在用户要求克制的正式成片中，为凑验收强塞强转场。资源定点测试使用明确授权的候选版本，正式方案仍遵守业务需要。

### 5.7 本轮资源验收范围

全量发现索引一次建好；运行与视觉认证分批覆盖六场景需要的代表能力。至少覆盖主体展示、步骤标注、详情 callout、系列布局、促销信息层、问答结构、标题、字幕和转场；可由同一资源复用，不规定必须安装多少个组件。

每个场景的关键资源都有一条真实装配到商品素材的例子。未通过部分显示未验证，不以“目录有几百条”替代可用性。没有适合资源时，允许受控原生编排，但记录原因，不能让全片悄悄退回固定大字卡模板。

## 六、音频与字幕：先建立资源模型，再接 MiniMax

### 6.1 一段成片不等于一条混死的声音

至少独立管理：现场原声、旁白、背景音乐、音效、逐字／逐句字幕、营销／步骤文字。每段声音保留稳定 ID、来源、文件、时长、源偏移、时间线位置、音量、处理方式和版本。字幕另外保留文本、时间、样式与来源音轨关系。

原生工程和可追溯计划是后续修改的依据，MP4 是输出。只有混合音轨的成片不能假装已经有独立旁白和背景音乐；只有烧录文字的视频不能假装可以直接删除原字幕。这时需源工程／独立素材，或明确说明分离、覆盖等方法的局限，不能宣称无损恢复。

### 6.2 修改影响矩阵

| 用户修改 | 允许变化 | 默认保持 | 是否需要供应商生成 |
|---|---|---|---|
| 字体、颜色、字幕位置 | 文字样式和相应视觉渲染 | 镜头、声音、文字事实 | 不需要。 |
| 缩短营销文案／步骤说明 | 对应文字及阅读停留复核 | 未关联的旁白和镜头 | 通常不需要。 |
| 修改真实口播字幕的内容 | 先区分纠错、断句和改写 | 音频事实不能被悄悄改写 | 改写所说内容时需协商并处理旁白。 |
| 更换本地背景音乐 | 音乐、混音、最终封装 | 已定镜头与字幕 | 不需要。 |
| 降低音乐／调整淡出 | 对应声轨处理 | 旁白源文件、镜头 | 不需要。 |
| 更换旁白音色 | 旁白及对应时序复核 | 已定商品素材、事实 | 有接口且用户授权时生成相关旁白。 |
| 改一句已读出的文案 | 对应旁白段、关联字幕及必要时长 | 其他句段和非相关镜头 | 仅相关句段；需防拼接听感突变。 |
| 替换某镜头为已有素材 | 该镜头及声画／布局依赖 | 其他稳定对象 | 不调用视频生成。 |

“没有重新生成素材”不等于“完全不渲染”。文字变化通常需要重新渲染视觉；只换音乐可以优先重混音和封装。用对象、输入哈希和调用记录证明保持范围，而不是要求重新编码后的 MP4 字节完全相同。

### 6.3 MiniMax 接口配置建议

分离语音生成、音色目录、音乐生成三个能力开关。官方分别提供 TTS、可用音色查询和音乐生成接口；它们不是一个“音频接口”的同一个能力，也不保证用户账号全部可用。[M1][M2][M3]

非密钥配置包括服务地址／区域、语音模型、音乐模型、音色 ID、语速、音量、音调、输出格式、采样率、字幕策略、超时、调用预算、缓存与重试策略。字段名由下一步对接既有配置决定，不在本稿编造已经存在的环境变量。

密钥只从服务端安全配置读取；`.env` 不提交、不打包、不放浏览器、不放 Prompt 或错误回显。音色用真实接口结果和试听文件登记，不根据中文名称随意编 voice_id。返回临时下载地址的声音及时落地并记录哈希，不能把短期 URL 当长期工程资产。

官方当前 TTS 文档提供字幕相关选项及粒度；具体返回形式和模型支持以实际账号／接口响应验证，不硬编码“只有句级”或“一定词级”。导入字幕后仍需映射到主时间线并检查实际声音，文本字数不能代替真实时长。[M1]

只有 TTS 可用时，可以生成旁白，背景音乐仍使用用户上传／已有授权音乐；音乐生成不应成为旁白功能的前提。未拿到 Key 时的连接状态明确为未配置，不将本地测试替身计为供应商成功。

### 6.4 混音由工程负责，不把任务丢给 TTS

先测量真实声音长度、空白、峰值、音量关系，再放到时间线上；音乐不能盖住语音，声音结尾不能被生硬切断。保留动作声的教程不能一键清除全部原声。

HyperFrames 当前上游已提供独立音频 skill，涉及淡入淡出、音量、音效链和自动化等，并把找音乐／生成声音与混音职责分开。[H2] 但本项目代码校验的是固定运行版本，因此必须验证本地预览和导出是否都支持所需能力。支持则走原生配置；不支持则通过受控音频预处理生成派生文件并保留可编辑处理说明。不能只让浏览器听起来变了，最终 MP4 仍是原混音。

换音色后时长变长：先尝试合理语速或经用户允许的精简，不自动牺牲关键动作。必须调整的字幕与节奏范围应明确；不能承诺所有音色替换都不影响时序。

## 七、米家 V2 怎样从参考片变成 Agent 能力

首先核对本地是否有参考原片、原始素材和可编辑工程。仓库登记的是本地参考成品，干净检出可能没有视频文件；缺少时只能说明缺少对应材料，不能假装已经观看或自动复刻。

有源工程时提炼的是可复用原则：镜头选择、主体大小、文字层级、留白、颜色、转场位置、声音层次、结尾结构。把其中有用部分转为有输入槽位、有约束、有实际调用路径的视觉模板与适配资源，而不是复制商品名和定制 HTML。

建立三层对照：原始素材；米家 V2 参考；自有 Agent 输出。前两者帮助看增值，第三者必须由现有 WebUI 创建并留下 runId、场景、源区间、资源记录、工程和 revision。源工程不可用时，不能声称已经从 MP4 恢复完全可编辑层。

至少做一次迁移验证：不给同一商品固定脚本，用另一批未参与模板调优的同类素材和普通需求自动出候选。再做“同素材、不同目标”验证：上新与教程应有可解释差异；教程素材不足就正确阻断，而不是硬做。

视觉比较不以模型自报分数为最终验收。先否决错商品、虚构事实、关键动作缺失、遮挡、不同步等硬问题，再评价构图、节奏、文字、转场、声音和完整性。机器给证据和建议，最终用户完整观片和听感确认单独记录。

## 八、现有 WebUI：不另建孤立 Demo

保留当前对话区和作品／工程入口。输入区下方的场景选择支持自动判断和六类业务定义；未接通的场景标注清楚，不能只让下拉有选项却暗中走上新模板。旧工程继续可看可改。

输入界面重点是素材、业务要求和声音约束。制作中展示真实阶段、已处理范围、当前阻塞与可恢复动作；不显示伪造百分比。完成后展示播放器、简短的制作说明、版本、可编辑资源和修改入口。详细资源 trace 放详情，不把复杂性推给商家。

示例说明：“已按上新片组织整体、佩戴和两处细节；未加入价格和性能主张；保留无旁白要求。”这比显示几十条工具日志更有用。

声音区允许选择原声、旁白、音乐、音色和字幕样式，实际是否可操作取决于当前资源和已配置供应商。用户可以说“音乐小一点，字幕挪开产品”，也可以在对应对象上修改。

## 九、连续编辑、恢复和工程交付

每次修改先记录基准 revision、目标对象、保持对象及依赖影响。保存意图操作和实际对象变更，导出新版本，不覆盖老成片。编辑过程中刷新／重启后能恢复当前工程与任务，不额外触发供应商生成。

工程包应包含实际可编辑 HyperFrames 源文件／原生结构、可移植相对素材引用、所用资源与版本、声音字幕层、编辑历史和重开入口说明。内部计划 JSON 可以保留，但不是原生工程的替代。项目代理 Key、私有凭据和无分发权字体不能打包。

真实验证在干净工作目录导入 → 重开 → 改一个文字对象 → 再导出；不能只证明 zip 能下载或能解压。

## 十、分阶段收口，不再用大任务吞掉验收

| 阶段 | 只解决什么 | 该阶段结果 |
|---|---|---|
| P0 事实基线与规则对齐 | 确认当前入口、版本、真实调用链与未完成项；将新会议目标覆盖旧执行计划 | 实际接入图、缺口台账、验收材料清单；不以文档完成冒充功能完成。 |
| P1 自动导演与 A／B | 把已设计的场景规则接入真实用户请求、素材理解和选段；复用最小可靠资源 | 上新与教程各一条自有 Agent 候选；缺步骤反例正确反馈。 |
| P2 资源差异化 | 全量发现、中文意图、兼容过滤、资源真实装配、米家方法迁移 | 有具体选择和渲染证据；未知资源不假可用；旧候选在同工程改进。 |
| P3 音频和续改 | 声轨／字幕资源化、局部改动、恢复和原生包闭环；预留 MiniMax | 未提供 Key 时也能真实换本地音乐、改字幕、重开续改。 |
| P4 其余四场景 | 依次接通详情、系列、促销、FAQ，不重写底座 | 各一条真实素材候选、对应负例与一次续改；逐项开放而非一口气宣布。 |
| P5 整体验收 | 全部场景与共用链路复验、保留通过项、处理回归 | 完成矩阵、实际视频／工程／记录、待人评或明确阻塞。 |

P1—P3 是首批验收，不是“剩余问题全部解决”。只有 P4、P5 也达到门槛后才讨论本阶段整体收尾。MiniMax 真调用另列“待用户提供接口”，不能写通过，也不阻塞已有素材与声音编辑核心。

## 十一、最终验收矩阵

| 编号 | 必须验证的用户行为／反例 | 通过证据 |
|---|---|---|
| G01 | 新会话只输入普通业务要求 | 实际配置加载记录；不依赖终端补 Prompt。 |
| G02 | 同素材提出上新与教程两种目的 | 结构、选段、资源不同，理由对应目标。 |
| G03 | 教程缺关键动作 | 明确缺失步骤／区间，不输出伪完整教程。 |
| G04 | “更克制，文字别挡商品”未给组件名 | 功能意图、真实召回、筛选和当前素材绑定。 |
| G05 | 指定某一处 Chromatic Radial Split | 仅指定范围生效，无演示占位，非静默替代。 |
| G06 | 用户禁止强转场或音乐 | 模板和 skill 默认不能覆盖禁止项。 |
| G07 | 目录资源缺依赖／版本不兼容 | 明确状态和原因，不假成功、不过度升级。 |
| G08 | 调整字幕外观 | 视频生成和 TTS 新调用均为 0；声音资产保持。 |
| G09 | 换本地背景音乐 | 仅相应声音依赖改变，镜头与文字保持。 |
| G10 | 换一个镜头为已有备选片段 | 局部替换，其他对象保留，不生成新镜头。 |
| G11 | 修改已朗读的活动日期 | 画面与声音一致，冲突需说明，不交付矛盾正式片。 |
| G12 | 进行中刷新／重启 | 相同任务恢复，无重复提交；项目不丢失。 |
| G13 | 原生工程导出后换目录重开 | 能改文字并再次导出，资源路径不依赖原绝对目录。 |
| G14 | 其余四场景各自普通请求 | 每个场景真实候选、场景特有负例和续改。 |
| G15 | 未参与调优的素材 | 不依赖固定文件名、预置 MP4 或特定品牌脚本。 |
| G16 | 视觉与听感审查 | 明确实际覆盖、具体时间点、问题、修复和真人状态。 |
| G17 | MiniMax 未配置／只有 TTS 可用 | 功能边界准确，其他本地编辑不受牵连。 |

这是验收设计，不是已执行结果。自动测试、浏览器、渲染、供应商调用和真人认可分别记录，不互相替代。状态不使用笼统“全通过”；保留失败证据和准确阻塞。
