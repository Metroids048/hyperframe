# HyperFrame 会议后收口：Codex 分阶段实施 Prompt

用途：用户确认业务文本后，交给本地 Codex 执行。本文不是本轮已完成的代码修改。

配套文件：`01_六场景业务设计_文本版.md`、`02_Agent自动化与资源音频收口方案.md`。也可直接读取合并版 `HyperFrame_会议后完整方案.md` 的对应部分。

## 总启动 Prompt

你在当前本地 Metroids048/hyperframe 项目中实施会议后的电商视频 Agent 收口。唯一仓库是 https://github.com/Metroids048/hyperframe 。

先读取本地实际存在的工作区规则、AGENTS.md、agent.md、codex.md，以及本任务包的业务文本和收口方案。核对 origin、HEAD、当前分支与未提交改动。保护原有源码、素材、缓存、工程和历史，不 reset、不 clean、不强制同步覆盖本地更改。

新的最高业务方向：暂停新的 AI 视频镜头生成，使用已有商品素材完成 Agent 自动制作和持续编辑。不要再执行旧 R2 中要求 RunningHub 真生图／生视频的验收项，不让其 Key 或余额阻塞本轮。保留既有生成模块，但本轮不扩展、不绕道调用。继续支持剪辑、文字、动效、音频、渲染与导出。

MiniMax API 由用户后续提供。现在先做好独立声音／字幕资源及本地音频编辑，不编造 Key、模型调用、音色 ID 或供应商通过记录。真实 MiniMax 验收单独列待接入。

不要再建平行 WebUI、另一套 Agent、多 Agent 讨论框架或独立资源平台。先检查并复用当前运行时 Prompt、场景包、AgentKernel、生产与编辑链路、资源目录、适配器、缓存、版本和原生工程导出。文档存在不等于功能完成。

按 P0→P1→P2→P3→P4→P5 推进，每个阶段独立验收并保存真实证据；通过部分封存，只对必要依赖修改。不要只做 P0 文档就结束，也不要同时散开六个未完成 Demo。当前执行阶段、已完成验收、失败证据、下一动作和外部阻塞写入项目已有状态机制；没有该机制时建立一份小型状态台账，不新造监督平台。

所有代码先本地运行和检查。自动测试和模拟供应商可用于开发，但必须标记，不作为真实 WebUI／实际模型／供应商／真人验收。遇到内部代码、素材映射、运行时、浏览器、渲染或测试失败，定位原因、修复、复测；不能只总结成“后续再做”。同类修复反复无效时换诊断路径，设置并遵守可见的调用和修复预算，不能无限重试。

确有无法由代码解决的外部依赖时，一次说明受影响分支、最小缺项和恢复步骤；继续不受影响的部分。停止或中断时写清检查点、实际状态和下一命令，不宣称会在无人执行时自动继续。

下面各阶段 Prompt 是阶段执行合同，逐段完成，不要求用户为每个视频另写技术指导。

## P0：实际调用链与旧计划纠偏

先读取以下当前文件，并以实际代码为准追踪调用，不依赖旧报告假设：
`lib/creative/contracts.mjs`、`production.mjs`、`scene-package.mjs`、`capabilities.mjs`、`resource-catalog.mjs`、`commerce-directors.mjs`、`prompts/commerce/manifest.json`，以及它们实际调用的 WebUI、编辑、声音和导出路径。

核对真实 WebUI 请求从哪里创建、如何确定 pipelineVersion、如何选择场景、何时加载 Prompt、如何查资源、怎样生成原生工程和处理续改。特别检查 pipelineVersion 默认与 v3 条件，但不未经验证就改默认值。

对每个缺口标注：已有并接通／已有但未贯通／需要新增／仅缺真实验收／外部阻塞。列出具体调用位置、最小改动、证明方式。读取六场景文本，统一 product_howto、product_demo、demo 等别名，保留历史项目 ID。

保存当前可以运行的基线与失败项，核实可用的真实素材。米家 V2 只能列为参考；原片、源工程或素材缺失时说明实际情况，不能虚构它们已存在。

验收：有实际请求到导出／续改的调用说明，有新方向覆盖旧计划的记录，有明确 P1 测试输入。P0 完成只是进入实施，不得称项目完成。

## P1：普通需求进入自动导演流程，先完成 A／B

依据已确认业务文本，把 A 上新和 B 操作演示的规则映射到已有运行时 Prompt、场景包和合同。保持现有阶段职责，更新 manifest、hash 与缓存影响。不要仅把文本复制进 docs。

明确每个阶段只加载需要的规则，并保留加载记录。补齐业务目标、素材证据、镜头源区间、必要动作依赖、保护区、独立文字和声音合同。足够信息时直接制作候选，不要求用户逐秒指导；缺关键动作时给精确补料说明。

从现有 WebUI 新会话分别输入普通上新需求和教程需求。不能通过终端传手写分镜、固定品牌专用脚本或预置 MP4。先用已有可靠资源跑通，不在本阶段横向扩展所有动效。

用同一素材集分别测试上新目标和教程目标：结果应在选段、结构、说明和资源上有合理差异；素材不能支持完整教程时正确说明缺口。另做一条关键步骤缺失的反例，不允许文字或图片补假操作。

验收：A、B 各一条实际素材、真实 Agent 链路生成的可播放候选与原生工程；有规则加载、源区间和步骤记录；反例正确。最终真人观片单列待确认，不自填通过。若缺必要真实素材，明确哪条不能验收，而非用合成夹具冒充。

## P2：全量资源发现、场景化选择与真实执行

在现有 HyperFramesResourceCatalog、CapabilityCatalog 和适配机制上升级，不另建一套与生产脱离的索引。扫描配置的本地 HyperFrames 根目录和实际可读资源，记录路径、版本、依赖、功能标签、执行类型和未能解析项。

覆盖 template、composition、component、effect、transition、skill、caption、typography、lower third、shader 等功能，但不要声称它们就是官方目录。skill 是规则指导，example 是参考，运行对象有各自输入契约。

把中文需求转成具体功能意图，必要时产生英文检索词；过滤画幅、素材类型／数量、源区间、动作保护、文字容量和运行时条件，再排序。先检查本地版本支持的检索能力，不为最新文档盲目升级、下载模型或调用外部服务。

资源区分发现、适配、绑定、当前条件渲染通过。新资源先在隔离环境适配和验证，再接入主工程；保持现有安全原生 bundle 和受控工具边界。真实记录候选、拒绝原因、实际选中资源、适配方法、路径、哈希、参数、输入和生效时段。

至少验证普通需求“克制、文字不挡产品、突出细节”能触发正确资源，不要求用户输入名称。再独立验证“仅某一处使用 Chromatic Radial Split”：必须作用于本次商品镜头，不能返回 SCENE A／SCENE B 或官方示例卡。明确要求的效果不能静默换成别的。

从米家参考中提炼可迁移视觉原则与输入槽位。不可用时说明没有观察证据，不编造复盘。用未参与调优的一组素材检验同一资源机制，避免固定文件名和商品专用脚本。

验收：全量扫描有边界和未完成项；实际使用的能力有绑定和渲染证据；两种自然语言需求、否定要求、范围要求、缺依赖反例均有记录；已有 A／B 工程得到可解释的改进，不另做孤立参考片。

## P3：声音资源化、局部续改与可恢复原生工程

分别管理原声、旁白、音乐、音效、逐句／逐字字幕、营销／步骤文字。每项有稳定 ID、来源、文件、时间线位置、处理和版本，并建立必要关联。优先使用现有声音与字幕模块，不以接入供应商替代声音工程。

当前先用本地音频从 WebUI 实测：改变字幕外观；换背景音乐；降低音乐并调整片尾声音；替换一个镜头为已有备选。每次沿用同一项目，保存 revision、计划改动、保持对象、实际变化和供应商调用数。不得生成新视频镜头。

字幕样式修改不能重新合成旁白；转写字幕与营销字要区分。改动已被朗读的事实时处理关联旁白，不能交付声画矛盾。换音色产生时长差异时复核相关时序，不能自动破坏教程动作。

配置 MiniMax 适配边界：语音、音色目录、可选音乐生成分别管理；模型、服务区域、音色和预算为配置；密钥仅服务端。未提供 Key 时精确显示未配置。模拟响应可以测试适配层，但真实调用验收仍待完成。

检查本地 HyperFrames 版本的混音和自动化能力。原生支持则使用；不支持时以受控预处理派生音频实现并保留参数。必须比较预览与实际 MP4，不只改播放器声音。

真实执行一次任务中刷新／服务重启恢复。导出原生工程到新目录，重开、改文字、再导出。保留相对引用、实际可编辑结构与必要素材，不能仅交一个 JSON 或 zip 空壳。

验收：同一项目至少三次连续局部修改；保持对象和调用数有证据；恢复不丢任务；干净目录重开再导出通过；不伪造供应商或真人状态。

## P4：把剩余四场景接通，而不是只增加四个名称

按 C 详情→D 系列→E 促销→F 问答逐条推进，共用已有导演、资源、声音、工程与审查链路。

每个场景完整映射画像、输入输出、故事原则、素材政策、资源、声音、编辑和质量规则。每完成一个，使用真实素材从 WebUI 给普通需求，交付候选及工程，并做一次局部续改。

专门负例：详情没有证据不得造参数；系列不能串商品身份／事实；促销缺价格不得造优惠，活动时间修改需同步相关文本和声音；FAQ 必须回答原问题，不用上新口号替代，缺证据不做绝对承诺。

只有设计或规则测试完成的场景标为该状态，不给“已可用”徽标。未接通时不能暗中路由到上新并宣称满足。不要用 A／B 的通过填其他四类。

验收：四个场景分别有真实请求、候选、原生工程、关键负例和续改证据。通过一个封存一个，依赖变更再做必要回归。

## P5：最终验收与准确收尾

对照收口方案 G01—G17 逐项实际执行。检查从新会话开始、同素材不同目的、未调优素材、目录缺依赖、用户否定要求、字幕／音频局部修改、恢复、跨目录工程导入和重新导出。

最终完整播放各场景的实际 MP4；自动检查画面和音频可以辅助，声明实际观察与试听范围。每个问题关联需求、具体时间、证据、影响和最小修复。没有试听能力就保留听感待审，不编造“完整观片听感通过”。人工确认只能来自真实用户反馈。

最终报告只写事实：仓库／HEAD、实际改动、命令及退出结果、每个场景所到状态、使用的资源与版本、每次编辑的改动／保持范围、实际文件路径、恢复／导入结果、未完成项和最小外部阻塞。

不能以几十条测试数字替代能看的片和能改的工程。P1—P3 完成只称首批能力闭环；P4—P5 也通过后才称本轮核心收口。MiniMax 若仍未提供，就准确列“预留完成，真实接入未验收”，而不是全项目 100% 完成。
