# HyperFrames 电商视频 Agent：改后审查与下一步收敛方案

审查日期：2026-09-12。远端快照：`6d85be33480bb4b07c354d66082e43db14c32d37`；上一版基线：`4848b72ec4584f9777f223e9537c52555bfec456`。

性质：基于源码、GitHub Actions 实际状态/日志、仓库实施报告及上一版需求的审查与待执行设计。未修改仓库，未在用户 Windows 工作区运行代码，也未直接观看 C1/C3/A2 本地完整视频。本报告中的验收阈值是项目目标，不是已达到的指标。

## 1. 核心结论

这次改动是实质性的：默认模型创作已接入分阶段 AgentKernel；官方技能与蓝图按阶段进入上下文；静态关键帧、动画制作、预览复核分开；原生工程、资源收据、字体和恢复能力得到扩展。[S1–S5]

但“应用稳定做出接近直接 Codex 的高质量视频”尚未证明。开发记录承认 60 秒设计仍朴素，90/120/180 秒尚无完整产品成片，缺少独立质量评审。最新远端电商 CI 也未通过。[S6–S9]

下一步不是重建系统或再扩一轮功能，而是：恢复可验证基线 → 修复观察与错误路由 → 将常规镜头变成可靠的资源复用 → 提前验证视觉方向 → 完成 60 秒质量闭环 → 再推进 90/120 秒。

保留现有 WebUI、登录/模型提供方案、HyperFrames 0.8.33、原生对象与历史。继续排除自动接入生图、生视频、数字人、新收费服务、广告投放及复杂多 Agent 平台。场景是检索和测试标签，不是用户必须选择的菜单。

- `runner.mjs` 默认模型分支调用 `produceDocument`，显式 legacy 开关才进入旧模型链路。

- `capabilities.mjs` 校验官方资源哈希、加载阶段技能与引用、生成适配收据，并保存惰性参考资源包。

- 原生版本、局部编辑、导出绑定版本和恢复基础不能回退为“整片 MP4 再剪一次”。

## 3. 已定位的问题与处理方向

### F01：CI 红灯与验收口径漂移

最新提交的 `Commerce native pipeline` run 34675877194 失败；`Conversational editing checks` run 34675877198 通过。电商失败位于 `test-commerce-fixtures.mjs:47`：第一个样例期待 `image-pan-zoom`，实际为 `split-detail`。后续原生检查、30 秒竖屏渲染和证据上传被跳过。[S7–S10]

这是测试期望与当前规则导演不一致的可复现问题，不能直接推断产品主模型创作损坏。需要先确认应保留哪种行为；若新行为正确，则更新对应预期并保留独立的时长、资源、对象、图层和输出断言。不能删除断言、跳过任务或回退设计只为变绿。

同时，现有 CI 明确不进行鉴权模型、真实 ASR/TTS 和人工质量验证。当前 `verify-editor` 清单也没有覆盖新增阶段生产系统的所有定向测试。应盘点新测试并显式接入离线/真实媒体层，不能让“旧剪辑 CI 绿”代表新创作全通过。[S10–S11]

### F02：资源真实进入了模型上下文，但还没有充分变成可直接复用的制作能力

当前实际候选注册为 7 个 recipe。按词片段匹配评分，主流程过滤后截取前三个，再让资源规划模型选择；整片共享这个选择。`adapt` 主要给模型新写的 source 加入版本、颜色 tokens 和来源收据，而非直接安装并参数化执行上游组件。[S2、S4]

这不算“假接入”，但也不能说完整模板/插件体系已被应用掌握。风险在于：选材和创意受到过早的少量候选限制；每次又重新写相似镜头，质量与成本都不稳定。

下一步：按本片表达任务召回资源，按镜头角色再选择；输入、版本、中文字数、画幅和授权是硬过滤，审美匹配是排序。保留原创出口，但把常见商品亮相、细节标注、双栏解释、字幕强调等变成真正的受审原生适配器。资源数不是验收目标，是否参与最终对象与输出才是。

### F03：多阶段链路已接通，但常规镜头也走昂贵的原创流程

主循环会对每个镜头调用 `scene.author`。首轮正常路径包含静态 R5、静态评审 R6、动画 R5；之后还有整片分批复核。组装时有 source 的镜头统一成为 `custom-native`。[S4、S12]

因此，长片会累计较多模型往返和失效机会。这里的根因假设需要通过调用日志测量，不能只凭代码估算端到端耗时。

建议内部加入按需求选用的制作方式：

| 制作方式 | 适用情况 | 实现要求 |
|---|---|---|
| 保持实拍/精剪 | 画面本身足够，不需新包装 | 不为走流程强画标题或增加无意义动画 |
| 参数化原生资源 | 成熟布局/字幕/标注已适合任务 | 直接填数据和调整参数，保留稳定对象 |
| 资源组合与适配 | 需要多个资源协同 | 按合同组合，局部模型适配，不能只换颜色 |
| 受控原创 | 现有资源无法表达或质量达不到 | 限定镜头生成源码，完整检查、局部修复 |

以上是建议内部策略，不是新用户菜单，也不是允许默默降低质量的“快速模式”。工具安全边界保持不变。

### F04：补充观察的证据没有被一致地传给后续阶段

`storyImages` 优先返回最新一组补充观察图。历史记录仍以元数据保存，但先前关键图片并不全部重新进入本次模型视觉输入。`replanSourceShot` 又使用初始 `evidenceImages`，附加记录只取 broad inspections，没有同样传入 action inspections。[S4]

因此，代码确有“不同阶段拿到的证据集不一致”；这是否导致具体 L90/L120 失败，仍要对照那些任务的真实输入日志验证。

建议建立可持续更新的素材证据索引：资产哈希、真实源区间、用途/动作、置信度、不确定原因、帧/代理引用、已检索区间。规划和修复都通过相同查询拿到目标区间及相邻边界证据，必要时保留整体上下文。不是把所有抽帧永远塞进每次请求。

观察预算按素材规模、已覆盖信息和问题重要性分配，设明确上限。区分“没有观察过”“观察后不确定”“确认没有该动作”“预算用完”“解码失败”。预算用完不能自动变成“用户缺素材”。连续动作结论必须匹配实际抽样或播放证据的精度。

### F05：错误分类仍会把某些问题交给错误的修复器

目前静态评审的 major 问题汇总为 `KEYFRAME_LAYOUT`；最终失败后，`scene.author` 会重规划源镜头。实际纯排版/对比度问题也可能走换镜头。首次全片复核还会把 minor 一并纳入修复集合。[S4]

下一步应将以下类别分开：

| 类别 | 应执行的修复 | 不允许的处理 |
|---|---|---|
| 文件、路径、解码、快照缺媒体 | 修复 I/O 或运行环境；重测同一输入 | 让模型重设计画面并消耗创意预算 |
| 模型超时/配额 | 保存检查点、分类等待/恢复；分析上下文体积 | 无限重试或擅自更换收费服务 |
| 源镜头、动作、商品关联不符 | 针对源区间补证据、局部选镜 | 只调 CSS 掩盖错误画面 |
| 布局、对比、裁切 | 改目标对象参数/局部源码 | 无理由更换正确商品素材 |
| 文字出现/退出时序 | 对照动画和用户要求改时序 | 把已要求退场的文字当缺失 |
| 已确认事实冲突 | 阻断发布级放行并修正事实绑定 | 通过改写声明让错误“看起来合理” |
| 轻微审美偏好 | 记录或进入有预算的改进 | 自动循环重做整片 |

保留有限修复，增加无进展检测；同一缺陷重复出现时升级定位，不清零旧失败记录。

### F06：早期方向预览仍然太晚

`previewRange` 在完整组装和最终预览复核之后才写入，并非用户等待长片时即可看到的早期方向样片。[S4、S6]

应从已确定的母工程中优先完成代表性镜头，提供 10—15 秒范围预览，绑定父工程、源时间、设计和资源哈希。范围检查不是整片通过；修改设计后只失效相关下游。不得另手写一个漂亮短片冒充后续完整项目。

### F07：当前主要评估“少犯错”，还需要明确“什么叫做得好”

现有预览评审主要识别遮挡、裁切、文字、动作和时序错误。这些必要，但不能保证商品片有主次、说服结构、设计差异和观看价值。

建议在已有 R4/R5 阶段增加明确的创意交付：本片唯一核心表达、开头为什么值得看、段落如何推进、关键视觉手法、品牌风格与素材依据、需要克制的地方。先审关键帧的效果，再整体完成，不能把“没有遮挡”当作“足够高级”。

摩卡壶 Q02 输入约束强调中性操作说明、原声与不编造参数；它适合测试选镜和制作，不能单独证明完整的电商营销能力。保留 Q02 作为回归；旗舰商品片还需要真实商品资料和可用品牌信息。缺资料时明确为中性展示/工程示例，不编造卖点、价格、评价或转化效果。

### F08：成果仍依赖机器路径，交付与文档状态需同步

实施报告的“尚未提交或推送”已落后于当前远端提交；证据主要指向 C 盘路径和本机端口。下一轮应生成可移交的证据清单，以 run/revision/工作区指纹绑定成片、源工程、输入和测试。使用适用的本地打包或经授权存储，不强制把大媒体和私有商家资料提交进 Git。

## 4. 下一步工作包：按结果逐项通过，不再八个 Loop 同时进行

### N0 · 可验证基线与 CI 修复

入口：当前本地工作区与已存在报告。改动：`test-commerce-fixtures.mjs`、相关 workflow、测试入口与实施状态文档。

任务：确认 CI 合同，修正不一致；列出新生产链测试与 CI 绑定；登记本地 A2/B/C1/C3 是否可访问；冻结 C3 revision/哈希；H03 原生母工程有效且不需重规划时可恢复导出。

验收：最新实际运行的必需 CI 不红；被跳过的渲染步骤重新执行；离线测试与真实模型测试分开；历史失败不改写；可用结果有可打开的索引。只写“准备通过”不计完成。

### N1 · 有针对性地修观察、错误分类与恢复

依赖：N0。改动：`production.mjs`、`source-inspection.mjs`、`recovery.mjs`、`hf-workspace.mjs`、必要的服务交互。

优先用现有 L90/L120、C4、静态排版失败样本验证，不跑全新大型队列。实现统一证据查询、按信息缺口补观察、分级预算、错误到处理器映射及无进展检测。仅分析受影响模块，避免全局重写。

验收：目标源区间的补充帧/哈希真实进入规划与修复请求；换对象不会丢历史证据；同一区间无需重复解码；纯布局失败不换素材；文件路径错误不耗创意重试；预算不足的 UI 不谎称素材不存在；补输入可以保留无关检查点。

### N2 · 实际资源复用与视觉方向闭环

依赖：N1；资源适配代码可在独立目录提前准备，但不得覆盖共享合同。

改动：`capabilities.mjs`、`production.mjs`、`story-validation.mjs`、`compiler.mjs`、`custom-source.mjs`、R3/R4/R5/R6、资源登记与测试。

按本次旗舰片的真实表达需求选资源，避免全库建设。把合适的官方场景/组件变成参数化、可编辑、兼容当前运行时的实现；保留受控原创。不要把“读取过蓝图后从头写代码”与“直接复用了可执行资源”混成同一状态。

在同一母工程先制作代表性开头、细节/说明和收尾镜头的设计帧，选择合适时段产出 10—15 秒范围预览。默认自主评估并推进，用户主动要求审批时尊重审批；这不是每轮反复问风格。

验收：至少有真正经过适配器复用的镜头，也能处理确需原创的镜头；资源 ID、文件/依赖哈希、处理器、对象 ID、检查证据一致；换商品/长中文/换画幅不过度依赖固定答案；范围预览先于全片制作结束；测量模型调用和等待是否减少，质量不能退化。

### N3 · 第一主门槛：60 秒产品质量与可重复性

依赖：N2。只保留一个新创作主任务，旧 C3/Q02 为回归对照，不同时启动所有长片和 holdout。

旗舰输入优先选本地已有、权利适用、同款商品的图片/实拍与确认商品资料；缺失的事实不能由模型猜。区分锁定事实、可见观察、允许的编辑性文案、不可使用的宣传声明。口播/配音/价格均按实际需求，不强制添加。

用简短商家请求通过真实 WebUI 独立制作至少两次（预算允许；不足就报告实际样本），保留全部失败。直接 Codex 参考与应用结果使用同输入、同依赖、同音频策略，尽量相近模型设置和工作预算；不能把参考整片源码直接拷入应用。

验收：完整 60 秒有信息推进，真实动作/声音正确；无凑时长；字体排版、商品主次和动效目的清楚；完整有声观看；对象可续改；局部修改、导出期间编辑、撤销、重开通过。内部拟定量表保留绝对 85/100 与相对合格参考差距不超过 5 分的目标，但须两位独立评审；未评审明确 pending，不自签质量通过。

### N4 · 90/120 秒与长任务恢复

依赖：N3 至少获得明确的质量问题闭环，避免在已知朴素方案上扩长。

基于原任务检查点逐个处理：90 秒先验证可用信息覆盖；120 秒复用匹配的 73.782 秒声音与词时间，按真实操作/图解安排余下时间，不拉慢声音，不要求每秒都配音。采用段落级时长预算与整数帧调度，减少模型因小数求和反复重做。

180 秒先复现具体非法 HTML 属性，判断是否是可安全扩展的能力或模型违约；仅修对应合同或源码，并测试负例。已完成镜头、声音与合法检查点保留；代码/资源合同改变时按依赖使受影响产物失效，不能盲复用旧通过状态。

验收：90/120 秒分别有真实完整成片、声音和后续编辑；取消/恢复通过且不污染上一版；未完成任务有可移交恢复包。600 秒继续只作为边界压力用例。

### N5 · 未见需求、商品可信性与交付

依赖：N3/N4 对应主能力完成。按被冻结的 10 个未见组合顺序运行，失败定位到已定义能力，不靠 case ID 或文件名特判。

增加明确的 SKU、价格条件、品牌和横竖方适配校验。发布状态至少区分：工程有效、视觉/声音审核、商品事实与授权、发布者最终确认。引用现行平台规则时重新核对，不承诺平台必过或转化效果。

验收：每个测试记录实际输入、run、revision、所用资源、完整输出、失败与修改；未执行项不得标通过；只有相应范围内的结果可以对外宣称可用。

## 5. 旧任务如何处理，不浪费已有产物

| 任务 | 先做什么 | 暂不做什么 |
|---|---|---|
| C3 | 固定当前版本、完整播放/试听、同输入比较具体差距 | 把已有片重新导出当成新生成 |
| C4 | 对固定失败输入重放路径/快照回归，再新建恢复记录 | 把已验证 4 秒回归写成 60 秒整片成功 |
| H03 | 核对母工程有效性，恢复已取消导出 | 无条件从需求解析开始重新花模型额度 |
| H02 | 分析每阶段载荷、响应与超时；保留两个镜头 | 继续简单提高超时或重跑全部镜头 |
| L90/L120 | 查询全部现有动作证据、确定尚未观察区域 | 把观察预算不足当用户资料不足 |

## 6. 运行时规则必须落入真实调用

### 观察规则增量

先查询既有证据索引，再请求新观察。结论标注依据与局限。只把观察确认没有的内容记 absent；未覆盖记 unobserved，低置信记 uncertain，预算不足记 budget_exhausted，解码失败记 media_error。场景规划与修复使用同一范围查询，相关旧证据不可被“最新一次”无条件替换。

### 资源与镜头规则增量

资源匹配按本片目的、镜头角色、素材条件、品牌和输出限制进行。关键词仅用于候选召回，不可把前三名当全片唯一选择。先判断应保持实拍、复用参数化资源、组合适配还是受控原创。不得为了资源收据数量或特效数量加入无意义效果；也不得为了少调用模型默默降级用户需求。

### 导演规则增量

每个段落说明观众新增理解了什么。事实及逐字指定文案不得变；允许的编辑性表达不得引入额外可验证商品承诺。动效服务信息层级、真实细节与节奏。不要只以“无错误”作为设计目标，也不把高级感固定解释为黑金配色、巨大标题或小角标。

### 质检与修复规则增量

先确定基础媒体有效，再做内容与视觉判断。问题输出类别、严重度、证据时刻、对象、可执行修复与不得修改项。对文字退场结合用户请求与动画声明；对声音只根据实际声音检查，不把静音浏览器播放当试听。轻微偏好不自动触发全片重做；修复验证后保留或回滚该局部版本。

## 7. 完成报告的固定口径

每个工作包分别记录“代码已接入”“定向测试通过”“真实模型已执行”“实际媒体/浏览器通过”“质量评审”“阻塞原因”。不再用一项总计测试数代替全部结论。

最终必须回答：此次改善了哪一个用户问题，修改了哪条真实主链路，用了哪些真正可执行资源，有哪条完整可观看成片，与旧版差异何在，连续修改有没有破坏内容，哪些能力仍然受限。
