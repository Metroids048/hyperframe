# 本机真实用户测试与视频内容评审

本文件由本地 Codex 执行，是 `FINAL_CLOSEOUT.md` 的验收附录。以下条款是工作要求，不是已经测试通过的声明。复用现有冻结合同、量表、检查器、浏览器工具和结果台账；不创建另一套平台。

## 一、先确定实际能力，避免“播放了就说看过了”

开始前记录：真实运行服务的目录/build/端口；浏览器是否能操作该本机服务；是否有图像观察能力；是否能真正获取视频片段序列；是否有获准音频感知工具；已有模型/声音/字幕能力及预算。

把证据分开：
- 浏览器从头播完、900/1800帧等是机械播放证据。
- 查看实际截图是画面抽样证据；不能由几张截图声称看过所有动作、听过声音。
- 查看源片与成片的连续帧/短片段是时序内容证据，应注明采样频率与未覆盖范围。
- 真实音频感知是听音证据；FFprobe有AAC流、ASR文字一致和静音播放都不能代替。
- Codex模拟商家/剪辑师是AI主观评审，不是真人用户研究。

工具能力缺失时，完成其余能验证的内容，生成完整审阅文件和具体待审时间段。不臆造听音，不拿“没有真人”作为不制作视频的理由，不擅自启用收费服务。

## 二、真实用户路径：只用产品公开的操作方式

### 1. 启动与输入

读取原冻结请求和资产，不读取或注入预制最终分镜。用现有 WebUI 新建测试工程，输入正常商家会说的话并上传原素材。允许用已安装的 Playwright/Puppeteer/CDP 等真实浏览器自动化完成操作，具体选型遵循本地工具；不要让用户改用终端。

正式请求从页面发出。网络/日志可用来观察与排障，禁止通过后端注入固定 plan、修改数据库状态、复制MP4让UI看起来完成。诊断脚本与正式用户验证必须分开记录。

先记录 request、上传素材顺序/ID/哈希、输出规格、声音要求、禁区、品牌规则及预算。逐字指定的文案必须逐字遵循；未指定的创意由应用自己设计，不能要求用户写导演级Prompt。

### 2. 生成过程

核对实际 job/run 与页面一致。等待过程展示阶段、失败和恢复，不将估算进度当真实完成。正式母工程未完成前显示同工程10—15秒代表范围预览：验证版本、源场景、时间范围、资源依赖和实际可播放性。

确认预览不仅是一段另写的精美素材；方向有主要问题时在母工程里修正，然后继续全片。不要为每条短片增加不必要的强制审核等待。

核对应用真实执行了哪些技能/资源、哪些复用、哪些原创；只引用名称或输出“已调用”不算证据。

### 3. 成片与内容

打开真实导出文件，而不是仅查看预览HTML；验证开头、中间、结尾和重要转场与预览一致。按第五节实施完整内容评审，不在参数合格时结束。

### 4. 连续修改

先完成冻结 I01—I12，按原要求累计10—14轮连续操作。以下是核对维度，不是替换旧用例的新固定台词：

| 行为 | 应观察的结果 |
|---|---|
| “只改第二幕标题” | 目标文字变化，其他镜头、声音、时长、素材与对象保持 |
| “去掉这段文字动画，内容和原声不变” | 合法静态成功；实拍仍正常播放，不因无叠层动画被拒绝 |
| “不要改价格，把标题缩短” | 否定约束不被误执行；价格对象保持 |
| “把标题换为包含‘撤销动效’这几个字的原文” | 引用文案不被当作撤销命令 |
| 复合要求 | 所有子句均满足才原子发布；失败保留上一有效版 |
| “只加字幕，不加配音” | 生成字幕但不调用新TTS；音轨保持原约定 |
| “只用第二张图” | 所有相关视图正确引用第二素材，不混入其他素材 |
| “价格先出现，条件不要漏” | 价格与活动条件的内容和时序正确，不被统一结尾规则覆盖 |
| “锁住开头结尾，只改中段” | 内容/布局/时间锁按原合同保持，邻接转场无破坏 |
| 选择性撤销 | 撤销目标修改，保留后续无关文字或声音修改 |
| 横、竖、方适配 | 重新排版、主体安全，不只居中裁切、缩小整屏 |
| 导出旧版本同时继续改新版本 | 输出绑定旧revision，编辑产生新revision，不串版本 |
| 重开/导入工程 | 可继续选中和修改原生对象，不只是播放一段扁平MP4 |
| 取消/重启恢复 | 已验证检查点复用，预算不复位，无重复发布、无遗留进程 |

每轮都保留原请求、实际工具调用、文档差异、实际画面/声音、版本关系。不可只测意图路由返回了什么。禁止拿用户唯一工程做破坏性故障注入。

### 5. 结果入口

在实际服务里逐个打开必需案例的最终视频、修改前后、母工程/可携带包和状态。验证HEAD、Range、MIME、seek、播放推进、完整结束与工程重开；200 HTML不是媒体成功。尚无作品的任务不出现虚假播放器，过期状态显示更新时间和版本，不假装实时。

测试停止/服务重启后再打开结果页，核对状态来源与文件一致。对外审查报告应可携带，不依赖审查者访问开发者的127.0.0.1。

## 三、内容审阅的两遍法

### 第一遍：先当观众，不替制作失败找理由

评审仅获得：用户短请求、适用平台/画幅、完整成片和必要的观看方式。不先看作者总结、自评分、耗时、调用数量、源码或“用了高级插件”的说明。

通过实际视频/连续画面回答：
1. 我能否说清在展示什么商品、这条视频要完成什么？
2. 最重要的卖点、特点、操作或活动信息是什么？画面是否提供对应内容？
3. 下一段为何值得看，是否反复展示同一状态或同一句空泛文案？
4. 风格、字体、色彩、节奏是否适合这件商品、这个人群和这次任务？
5. 看完后需要知道或执行的事情是否清楚？没有要求CTA的中性演示不强制带货。

回答缺失不能由导演脚本来补。脚本写了“展示细节”，成片没有看到细节，仍是失败。判断“这像普通图片轮播而不是该需求下合格广告”可以成立，但必须指出实际证据，不能因没有复杂动效就否定克制设计。

### 第二遍：结合事实、素材与用户合同查准确性

读取商品事实、获准素材、原文、禁区和编辑范围。把第一遍判断对照到具体时间与对象：是否错款、串图、暗示不支持的性能、编造评价、遗漏优惠门槛、误剪操作、删除口播限定条件、把多画幅处理成危险裁切。

检查影片完整性与目的，不强求每一秒都有新知识。呼吸、情绪、完整动作和阅读停留可以合理存在；同样也不能让“品牌氛围”成为无内容拖时长的借口。

## 四、实际画面与声音怎么查看

全片至少完成一次真实1倍速播放的机械验证。视觉内容审阅覆盖所有镜头的关键可见时刻、信息变化和切点前后；连贯动作、字幕时序、转场和细节另取连续片段。不要只审一张联系表。

先低成本通览，发现运动/动作问题再加密对应范围。抽样频率、缩放和局限入日志；无法观测1帧的工具不能宣称帧级视觉判断。工程时钟可以帧精度测量，感知判断另行说明。

竖屏片至少在移动端代表显示尺寸（例如375px内容宽）和正常桌面尺寸观察。测试显示适配，不把“375px下字还有像素”当作可读性证明。标题、条件、字幕应能在合理观看时间看清；长文字可重排/分时显示，不是任意删字。

有声音的任务分开检查音轨结构、混音、转写/词时间和实际听感。要求保留原声时核对真实源区间，不用另一段声音填充。旁白不必塞满长片每秒，但必须完整、不生硬截断，且与画面对应。无声任务不因“多了音乐显得高级”擅自加声。

黑帧/冻结/重复检测只是线索：合理静止商品画面和特意黑底卡不能机械误判；意外黑帧、解码缺帧、循环素材凑时间应判硬缺陷。判断理由必须可复查。

## 五、质量量表与决策

沿用原冻结量表。原合同没有更具体权重时使用已约定默认：商品表达25、叙事20、视觉20、动效15、声音10、续改/交付10，总分100。每项先0—5打分，再乘权重/5；可用0.5分，但不要捏造小数精度。

| 维度 | 低分典型 | 合格高分应有的证据 |
|---|---|---|
| 商品表达25 | 商品不清、关键特征靠口号、错款/错事实 | 主体清晰，真实特征/卖点有对应画面，需求和观众匹配 |
| 叙事20 | 重复状态、随意拼段、长停留、信息断裂 | 开场切入清楚，各段有目的，动作/说明推进，收尾完整 |
| 视觉20 | 套通用卡片、品牌混乱、小字、遮挡 | 有整片视觉规则、信息层级和合适构图，多画幅安全 |
| 动效15 | 所有元素同时飞入、无意义缩放或轮播 | 动作服务产品/信息和节奏，静止与运动有取舍，seek稳定 |
| 声音10 | 生硬、突兀、盖住人声、字幕错时 | 符合原声/配音要求，语义、节奏、混音和字幕对应；听感有实际证据 |
| 续改/交付10 | 改一句重做全片、版本串线、工程打不开 | 改准、无关内容保持、恢复/重开/结果入口可信 |

分数锚点：0=没有或错误；1=严重失效；2=明显基础且需大量返工；3=可理解但需明显修改；4=接近发布、少量打磨；5=有证据的高完成度。不能只凭“使用了资源”给视觉/动效满分。

合法无声任务：按原量表既有规则调整；没有规则时在看结果前固定如何从其余90分归一为100，注明无声，不给声音虚假满分。有声音要求却没听音的任务，声音记未审，报告已审维度及剩余范围，不伪造完整总分。

原定85/100与合格同输入参考差距不超过5分继续作为质量目标。AI评审可以用相同尺度做主观判断和迭代，但标为AI估计；不等于两位真人签收。直接Codex参考要在同素材、同请求、相近模型/声音/预算下制作；差异如实记录，不能把官网不同商品成片作为同输入数值基准，也不能将参考整片代码注入产品。

硬违例优先：错商品/价格、虚构承诺、漏强制需求、必要文字长期不可读、非预期黑帧/截断、强制静音、改错锁定对象，任何一个都不能用平均85分抵消。

主要主观问题：明显模板化且不适合任务、信息推进不足、字幕层级/声音显著破坏理解、表现方法无法支撑要求。即使机器参数全过，也要继续修。

轻微偏好：两种都合理的配色、细微节奏喜好，在满足用户与固定量表时记录取舍，不无休止重做。

## 六、三个可直接调用的执行/评审 Prompt

将这些行为接入现有开发验证与应用制作后复核；按现有输出schema最小适配，不只把文档存进目录。

### A. 用户模拟测试 Prompt

```text
你是本项目的AI模拟电商用户测试者，不是真人评审。仅通过当前真实WebUI完成所分配的原冻结case。读取原请求、素材和约束，不读取预制分镜，不注入计划或缓存答案。
执行上传、普通需求发送、等待/观察、提前预览、全片、导出与所分配的连续修改。记录实际job/run/revision、URL、截图/媒体、请求、控制台/网络异常和可感知的交互问题。
应用必须自己完成设计；不要替它手工修最终工程。遇到故障收集首个因果证据，交给开发视角修复，再从原场景复验。
每个需求子句分别判满足/违反/未验证；负例按原预期判断。只调用HTTP成功或播放器出现不算通过。结束给实际结果及具体失败，不把自己称为真人、不用测试数量替代用户体验。
```

### B. 视频内容评审 Prompt

```text
你是独立的AI视频内容评审者。先不要看作者解释、源码、耗时或已有分数。用可用工具实际检查给定成片；明确直接看过哪些帧/片段、是否真实处理了声音。
第一遍作为目标观众描述：看到了什么商品、获得什么信息、为什么继续看、风格是否匹配、结尾是否完成任务。写不出来就记内容缺口，不用脚本代替成片。
第二遍读取原用户要求、商品事实与授权素材，逐项核对：商品/价格/文案、动作与卖点对应、叙事推进、视觉层级、移动端可读性、动效目的、声音与字幕、编辑范围。
列出保留的优点与具体问题。问题必须有revision、时间范围、实际证据、对应需求、严重性和可执行修复目标。不能空写“高级感不足”，也不能把静态设计或少动效天然判低分。不要为了达到门槛逐轮抬分。
按冻结量表给AI主观评分或未审项，硬违例优先于平均分。没有实际音频感知就不写已试听；只有抽帧不写完整看过连续动作。
你不负责让作者满意。返回明确的needs_repair / automated_review_passed / partially_reviewed判断；它不等于真人或商用最终签收。新的评审不看前一轮分数，后续由协调者比较前后证据。
```

### C. 根因修复与复验 Prompt

```text
根据这份有证据的失败记录工作。先判断问题属于环境/协议、媒体证据、用户意图、资源匹配、素材选择、布局/动画、声音/时序、编辑范围或版本交付。
只修与原问题相关的最小有效范围，保持用户锁定内容、事实、声音和稳定对象。共性问题进入公共生产逻辑与回归，不靠手工改最终HTML/MP4特判当前case。
原方案不适合表达目的时，选择新的叙事或资源组合，而不是重复加转场。参数本身错误时直接修参数，不重做整个镜头。
同范围比较修前修后，证明原问题减少且未引入新问题。修完重新通过真实UI复验相关请求，再完成全片衔接和受影响回归。
同因失败无新证据停止盲试并换诊断；预算沿用原计数。成功关闭该缺陷后继续下一项，不能把关闭一个问题当作任务完成。
```

建议记录结构（可映射到现有文件，不必增加新格式）：

```json
{
  "case_id": "实际case",
  "revision_id": "实际revision",
  "reviewer_type": "ai_independent_context",
  "viewing_evidence": {"frames": [], "clips": [], "audio_perceived": false, "unreviewed": []},
  "requirements": [{"source_quote": "原始要求", "status": "unverified", "evidence": []}],
  "strengths": [],
  "issues": [{"severity": "major", "time_range": [18, 24], "evidence": [], "requirement_ref": "原要求", "problem": "具体可见问题", "repair_goal": "具体改好标准", "keep_locked": []}],
  "scores": {},
  "verdict": "partially_reviewed"
}
```

上面时间、ID和状态只是结构示例，不是已发生的测试结果。填写时必须来自真实产物。

## 七、收口与回归：这次迭代要减少问题

先在母工程代表镜头上确认方向，再完整生成。主要问题按影响由大到小修复，不把所有minor一次性重做。每次内容修复记录目标、范围、修前后实际证据和剩余问题；独立评审不以过去分数为锚点。

任何共同代码修复，至少回归该次失败输入和一个同类但不同输入；已被调试的holdout要标记成回归，不能再称最终版本完全未见。预算允许且原框架支持时增加未用于调参的同类检查，但不改变原冻结清单、也不无限扩大测试。

所有正式结果没有已知硬违例和主要内容问题后，在拟交付build上完成一次真实用户全流程。通过后不再为了追求风格完美无限改动。等待用户或真人签收期间，保持完整作品可查看；结果入口、修改、工程、声音和授权未知项明确，不伪造“已经商用通过”。
