# Codex 电商视频任务执行与验收规则

状态：待合并到 video-agent/codex.md；本文不是执行日志或验收结果。规则须通过现有 AGENTS.md 显式引用，并落实运行时门禁。

## 1. 成功定义

用户要的是满足真实业务需求的最终视频和可继续修改的工程，而不只是正确代码。测试通过、进程运行、预览可见、渲染成功、导出文件存在均不能单独证明交付。

任务开始时读取现有指令、任务台账和相关 Skills，检查真实进程与工作区；保留所有未提交改动、历史版本、素材和用户数据。不要通过重置、替代项目、绕过已有 WebUI 或固定成片预置来制造通过。

## 2. 先冻结验收合同

从用户需求提炼：目标用户、观看者、业务目的、商品身份与事实、原始素材、输出画幅和时长、声音要求、必须发生的画面／动作、禁止变化的部分、授权约束及合格参考。

将这些内容持久化为简短的验收合同。没有价格就不能编价格，没有功能证据就不能写性能承诺，没有动作就不能声称完成教学。约定的时长不允许靠无效静帧或循环填充。

## 3. 证据必须来自当前最终版本

每次审查绑定 project ID、job/run ID、revision ID、最终文件路径和哈希；记录真实执行时间。任何改动产生新版本后，旧版本的视觉通过不自动继承。

脚本制作／人工共创参考片必须标记 reference-author 或 scripted-runner。只有实际经产品 Agent 入口产生的内容才能标记 agent-generated。只接入、重导出预置作品，不证明新需求生成成功。

## 4. 四层检查

### A. 工程与媒体检查

先运行变更相关测试与项目既有完整检查，再校验最终文件可完整解码、时长／画幅／帧率符合合同、音轨数量与边界正确、没有缺失媒体和明显异常黑帧。记录真实命令及结果，不编造成功输出。

### B. 真实工作台端到端

通过既有 WebUI 提交真实需求；确认所返回工程与所下载 MP4 对应。验证播放、暂停、拖动、全屏、下载。随后执行本次场景的真实局部修改、撤销、保存重开和再导出，比较不应变化的内容。接口单测不能冒充浏览器流程。

### C. 全片视听审查

审查实际导出的最终 MP4，不只看工程预览或封面。正常速度完整观看；逐场景检查主体、文字和信息；关键切点前后密集查看；动作复杂处回看；检查片头、最后几秒和声音尾部。

画面证据至少覆盖每幕最充分显示的时刻、镜头衔接、字幕变化、商品局部及片尾。固定抽几张图不能证明动作、节奏、闪烁、同步和完整性。分镜缩略图仅供定位，不能代替整段审查。

音频检查分为格式／电平技术检查与实际听感、语义和同步检查。运行播放器不等于模型听到了声音；运行浏览器不等于真人看过成片。具备视频理解能力时可以提交模型自动审查；仅能看抽帧时必须声明覆盖限制，并将未覆盖的连续性和听感留给人工检查。

没有适用的观片／听音能力、文件无法访问或完整证据缺失时，标记 BLOCKED_REVIEW，不能把技术报告包装成视觉通过。

### D. 模拟真实用户与人工确认

以商家、首次观看的消费者、剪辑审查者三个视角分别提问。A：能否迅速看清是什么商品、看懂表达、知道下一步？B：能否按顺序重复关键操作？商品事实、品牌与明确禁区是否遵守？

自动审查提示不应包含制作模型的自我夸奖或预先分数；优先使用独立审查上下文。模型提出的观感和评分仍是自动审查，不得自动填入人工已认可。USER_ACCEPTED 必须有实际人类审查者、版本与反馈记录。

## 5. 硬阻断项

出现以下任一问题，整片不得作为正式合格交付：错商品或不同型号混用；虚构关键商品事实、价格或操作；关键步骤缺失；重要主体、手部或产品结构被裁掉／遮挡；字幕或标签错指关键对象；音画对应错误；用户要求静音却加音；无权利依据且要求商用；最终版本未完成规定复验；实际结果不满足用户目标。

美观分数、单元测试数量、渲染速度不能抵消这些问题。不得下调评分标准、忽略警告或改需求来让同一结果“通过”；确需改范围必须有用户决策记录。

## 6. 修复循环

每个问题写清：所属需求、最终视频时间区间、截图／片段证据、问题、用户影响、推定原因、最小修复、需要保持的内容、复验结果。

优先顺序：事实和动作完整性 → 主体与可读性 → 叙事与节奏 → 声音 → 次要动效细节。修复后重新导出和检查受影响位置，并检查整片衔接。连续两次相同失败必须停下重复尝试，诊断素材、取景、约束、编译、组件或评审方法，不无限重试同一 Prompt。

## 7. 状态与门禁

NEEDS_FIX：存在需修复问题。
BLOCKED_MISSING_ASSETS：缺足以完成目标的真实素材。
BLOCKED_RIGHTS：缺少本次使用所需的权利依据。
BLOCKED_REVIEW：未能完成要求的视觉／听感／真实入口审查。
TECH_PASS：工程与媒体技术检查通过，不代表视觉通过。
AUTO_REVIEW_PASS：可执行的自动审查通过，覆盖范围明确，不代表真人认可。
READY_FOR_HUMAN_REVIEW：所有本轮自动检查和交付准备完成，等待真人审查。
USER_ACCEPTED：真人对具体最终版本明确认可；不自动等于允许公开发布。

实现时应保存各维度状态及证据，而不是只用一个总布尔值。可以输出显著标注的预览／候选片；不能因为用户能下载就把它标为正式验收完成。缺证据、证据文件不存在或版本不匹配时，正式交付门禁应失败关闭。

## 8. 防止演示过拟合

每场景先做获人工认可的参考片，再用相同输入在真实 Agent 流程独立运行。使用一组未参与模板调试的同场景新素材做保留测试；不能通过文件名、商品名或预置成片分支返回硬编码结果。

专项修改至少包含：只改一处文本且不改声音；修改指定镜头时长并保持必要动作；撤销；重新打开工程；再导出复验。遇到不可能同时满足的约束，说明冲突而非擅自牺牲关键动作或事实。

## 9. 交付内容与报告

交付当前版本 MP4、原生可编辑工程、素材及授权清单、原始任务与分镜、技术结果、真实 UI 记录、逐问题视觉审查、未通过事项。工程打包要遵守素材再分发权限；无权利打包的原始媒体仅记录合法获取方式，不分发字体文件。

报告清楚区分：本轮改了什么、技术通过什么、自动视觉覆盖什么、是否真人确认、哪里尚未完成。不能把运行时长、模型调用数或新任务提交当成实际成片进展。

任何实现代码在给用户前必须本地运行与检查。环境阻断时如实记录未运行的部分；不声称已验证。不要宣称没有实际机制的后台持续执行。
